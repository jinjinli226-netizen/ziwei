# E03 owned Profile / HOME frontend integration

User target: a newly created Bot has one dedicated named Hermes Profile whose native resolved HOME is the HOME actually used for its configuration, memory, sessions and runtime state. The already delivered focused main chat and original employee/main-conversation identity remain.

Implementation waits for E02's stable provisioning patch and exact API contract. The E02 ADR `fc0f3b61a47c45affc3db3679e5d453e1c8a9e51` supplies the initial shape below; these fields must be checked against the final contract before dependent UI code is connected.

1. Make the ordinary create dialog a single Bot creation request. Select the actual online computer, enter the Bot's name and optional role. Treat the discovered source Profile as an advanced initialization template, not the Bot's own identity. Let the server allocate the owned Profile name; do not submit HOME, ownership ID or a client independence flag.
2. Keep one idempotency key and exact original creation intent across a lost response. A 202 result selects the original Bot and tracks its original provisioning action. Pending, acknowledged or uncertain results expose read/recovery controls instead of another creation request. Persist request metadata only, scoped to actor, workspace and computer; never retain private instructions or credentials in storage.
3. Show the server's `instance.mode`, dedicated `instance.profile`, `templateProfile`, and the confirmed `instance.home`. Before a device receipt, show HOME as unconfirmed. Provisioning success does not imply authentication, validation or activation. Offer the existing validate/activate flow when the backend admits it, and surface authentication required as its own actionable state.
4. Recovery calls the documented versioned provision endpoint for the same Bot identity. Query pending/unknown original actions; after a definitive failure, explicit recovery may verify or complete that same Profile. Refresh, close/reentry, workspace or device changes must not adopt another request or change the original identity.
5. Legacy Bots and Creator employees retain their employee ID, main chat, source Profile and existing private instance HOME. Label their source/instance mode truthfully. No migration, profile deletion, shared Profile binding or directory recreation is included.
6. Keep phone setup on the same employee and workspace. Only the server-returned bot instance identity may authorize fixed owned Profile binding. Reuse the current phone setup without another Profile. Do not perform real phone actions in acceptance.
7. Verify with the actual product UI and installed Hermes in an isolated test HOME: two Bots get different named Profiles; native resolver HOME equals each Bot runtime HOME; same request/recovery creates no second employee/Profile/chat; rename preserves identity/HOME; authentication and unknown states stay honest; main chat opens and accepts a bounded native test-provider turn. Check the 390px create/status/main-chat path.
8. After E02's stable patch and focused verification, update the one persistent preview at 5283/4283 using its original stateRoot/native launch entry, fresh process checks and preservation proof. Until then, the existing `beac160a` preview remains running.

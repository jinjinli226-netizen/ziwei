# 紫薇扩展边界与原生能力复用

日期：2026-10-30。来源：用户本轮明确要求，以及 DSH 作者工作树的 `docs/ziwei-dsh-migration-contract.md`、`routines.rs`、紫薇 `src/hermes-native-contract.mjs`。本文件记录方向和真实接入边界，不代表动态网页插件宿主已实现。

## 决策

业务方法直接作为 Skill 使用，不再外包一层业务插件。MCP、CLI 和原生插件继续由各自运行环境加载；紫薇统一提供员工管理入口、目标设备投递和真实结果展示。DSH 的 Profile/Loader、Hermes 的原生配置分别是其能力事实源，不复制一套会覆盖原生配置的紫薇插件清单。

账号权限、员工身份、会话、消息队列、设备连接及执行回执保持稳定底座。新增扩展通过已授权员工与设备调用这些接口，不另建平行会话或调度系统。

## 主动工作

| 引擎 | 已存在的实现依据 | 接入方式与边界 |
| --- | --- | --- |
| DSH | 原生 Hub 的单 Bot Routine CRUD、启停、run、history、lastSessionId；新增紫薇具名 `routines.*` 设备操作 | 使用原生 scheduler 单独调度；紫薇展示原生任务与回执，不再复制相同 schedule。`submitted` 只代表接受提交，不能表示业务完成。 |
| Hermes | `src/hermes-native-contract.mjs` 的 goals、heartbeat、kanban；现有 Bot Routine/automation 绑定 | 保持现有原生运行和紫薇执行授权链。goals/heartbeat 的状态、启动、暂停、恢复、停止和 step 已有明确方法；新增界面应复用这些方法，不能把方法存在当成现场依赖已就绪。 |

调度者归属必须随任务明确，避免原生调度和平台调度重复触发同一任务。更换员工、设备或 Profile 后不能重放旧的未知执行。

## 后续扩展接口的四类贡献

这些是接口设计候选，目前未实现通用动态注册表或自动生成网页面板：

1. **执行贡献**：具名工具、命令或后台任务，声明输入/输出和执行预算。通过现有设备 action 调用，保留平台会话与来源。
2. **事件贡献**：定时、消息、设备和任务事件的订阅与处理。事件携带原来源标识；每个任务只有一个调度权威。
3. **界面贡献**：声明式配置 schema、工作面板和结果视图。配置归属原生引擎或扩展自身，紫薇不以任意代码字符串直接改写主页面。先复用真实 settings schema 编辑，再扩展有版本的界面贡献协议。
4. **生命周期贡献**：安装、启停、更新、卸载和健康状态。结果区分即时应用、新会话生效、页面刷新、进程重启及未知；保留原请求和部分完成情况。

未来由 AI 生成的模块应包含贡献声明、实现、配置 schema 与必要验证，再通过上述接口安装；不是要求 AI 每次修改紫薇主程序的菜单和路由。具体 SDK 和动态界面宿主需要单独实现与验收，本轮不凭设计文档宣称已经具备。

## 热插拔的真实边界

DSH 原生 Host Loader/Plugin Manager 支持有条件热应用和配置更新；其 `application` 与 restartReason 是最终依据。`no-hmr`、`package-moved`、`host-module`、`unmanaged-plugin` 等情况不能通过网页自行改写成 applied。已有内容的会话不能原地换 preset；必须明确新建并保留旧会话。

DSH 原生 Web 有客户端模块图、HMR 与插槽机制；当前 DSH Bot 的 `ui/*.js` 是 Rust 编译时内嵌的静态前端，没有承载这套通用客户端宿主。因此，Host 插件加载成功不证明其专属界面已经出现在 DSH Bot 或紫薇中。兼容原生客户端宿主与实现紫薇自己的声明式界面贡献协议是两种不同方案，后续应根据实际插件需求选用，不直接把 React 原生插件视为 Vue 组件。

改宿主 EXE/Rust 内嵌 UI 仍需构建发布；改紫薇稳定底座仍需正常发布。普通 Skill 或受支持原生插件的变更，按各自加载协议生效，不为采用插件理念重写这些机制。

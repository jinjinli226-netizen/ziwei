# Windows 客户端统一远程升级

## 操作入口

管理员在紫薇「团队管理 → 客户端升级」中选择具体电脑。页面显示该机当前 build、官方目标 build、在线状态及是否支持远程维护；没有选择全部电脑或自动升级全部设备的行为。

点击升级后，客户端暂停接入新的普通工作，等待这台电脑所有工作区的员工完成当前工作。已运行任务的可信协作子任务仍可完成，避免父任务与维护互相等待。等待期间可取消。运行中的手机 Gateway 也必须空闲，并由其监督器确认关闭后才进入更新。

维护由客户端本身领取，交给安装目录外的独立程序运行现有官方更新器，不依赖承载员工聊天的 Hermes 进程树。安装前检查固定官方下载地址、包 SHA-256 和本次目标 build；保留原安装位置、设备身份、连接与用户数据。更新器的完成回执不是上线证明，只有该宿主目标 build 的新进程真实认证心跳才确认成功。

旧客户端没有 `remote_client_update_v1` 能力时，界面明确提示先安装一次支持该功能的新版，不声称旧设备已可一键升级。首次升级仍可沿已核验的精确设备维护入口安排，或在该电脑执行官方 Windows 更新命令；源码验收阶段没有触发任何真实电脑升级。

## 协议与恢复

- 管理会话：`GET /api/workspaces/:slug/client-updates`；`POST /api/workspaces/:slug/devices/:id/client-updates`；精确请求查询和排队取消位于同路径 `/:requestId` 与 `/:requestId/cancel`。
- 设备凭据：`GET /a2a/v1/device-updates?workspace=…&deviceId=…` 只读发现；`POST /a2a/v1/device-updates/:requestId/claim` 和 `/progress` 显式领取、报告。设备凭据不能发起管理升级请求。
- 管理请求只接受稳定 `idempotencyKey` 与 `waitForIdle:true`，不接受任意命令、下载地址、强制停止或用户指定 build。服务器从固定官方发布清单保存不可变目标。
- 一份本机用户数据共享持久宿主标识，服务端每宿主只容纳一个未完成维护意图；标识用于互斥，不作为跨工作区访问授权。
- 页面刷新只查询；POST 回执丢失先恢复原请求，不自动换幂等键重发。取消只适用于尚未开始更新的排队阶段。
- 客户端保留受限本机账本和包外工作目录。异常、重启、创建 worker 与写账本之间的窗口均有恢复检查；活 worker 优先于服务端过期状态，不能因此重复安装。
- 服务端超过两小时未收到升级终态时，仅显示回执超时。用户显式重新请求才将旧维护意图记为未确认超时失败并保留原记录；这不证明旧进程已经退出。本机仍独立检查真实维护进程和原官方维护锁。
- 新版真实心跳可以满足尚未领取或尚未上报完成的同目标请求，避免旧 worker 最后完成、而新请求还绑定旧 build 时永久卡住。`completionSource:heartbeat` 只证明目标版本上线，不声称由某个具体请求启动更新器。

### 此次停止阻塞的实际原因

F 尝试失败后，最后核实的李金晋电脑仍为 build `161cc99010d6cdee4e3d8834135ac2ed4e8fb2031b746755b7d53de0b76dfb0b`、PID `34836`，没有新远程维护能力。它报告当前执行、轮询和隔离数量均为零，Gateway 为空；阻塞来自本地历史检查。

实际状态文件是完整约 2.86 MB JSON，包含 144 条 started、177 条 completed，未发现重复去重键。唯一非 legacy 孤立终态是 `action_b37893ca-7615-43a5-8996-f93bdacfdf19`：服务器原动作是在授权 HTTP 前置请求中超时，原错误为 `The operation was aborted due to timeout`；本地没有该旧任务的执行退出证据。另有三条 blocked delivery 已有真实 Windows Job 根进程和执行树退出证明、活动进程数零及退出码零，但手机业务结果仍不确定或服务端返回 400，不能把这些业务回执改写成成功。

G 修复将这些经分类的终态历史保留为 `LOCAL_HISTORY_RETAINED`，保留全部原始文件、任务结果和去重键。仅本地停止检查可返回 `safe:false` / `stopSafe:true`；正式保全扫描仍严格拒绝原有不确定历史，不能将本地可停止解释成旧任务已安全完成。真正未完成的执行、隔离、身份不一致、损坏状态或活 Gateway 仍阻塞停止。

候选安装包的 `recover_history` 新入口先核对当前精确实例、所有工作区空闲、新检查器的保留历史结论及原文件哈希，再保存私有快照和精确停止意图，用持有的 `System.Diagnostics.Process` 句柄停止该 daemon。若原生程序在停止后、写退出文件前出错，必须重新证实原 PID 缺席、该安装没有新 daemon、端口没有监听、配置与原文件不变，并持久保存独立缺席观察，才返回恢复成功继续更新。该观察只证明 daemon 已不在运行，回执始终保留 `originalExecutionExitConfirmed:false`，不补造旧任务退出。

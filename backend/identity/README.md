# Workspace unified identity implementation (preparation only)

Contract: identity 1.0.1 / CLI standard 1.3.0. This source is not a production identity cutover. Default mode is `legacy`; importing modules does not migrate any database. Only an explicit server `ZIWEI_IDENTITY_MODE=unified` enables the new tables, routes and guards. No production passwords, subjects, bindings or data are provisioned by this code.

## Server configuration

Required in unified mode:

- `ZIWEI_IDENTITY_ISSUER`: exact HTTPS issuer, without trailing slash. No default or candidate authentication domain.
- `ZIWEI_IDENTITY_API_SECRET`: confidential `ziwei-workspace-api` introspection secret.
- `ZIWEI_IDENTITY_WEB_SECRET`: confidential `ziwei-workspace-web` code/refresh/revocation secret.
- `ZIWEI_IDENTITY_SESSION_KEY`: base64url encoded 32 random bytes, injected securely and shared by runtimes using the same database. AES-256-GCM encrypts server token and login-transaction payloads.
- `ZIWEI_IDENTITY_ORIGIN`: optional exact origin, defaulting to the confirmed workspace origin `https://ziwei.qzelynth.top`; callback is always `/api/identity/callback` on this origin. It is never derived from Host, forwarded headers or request input.

Public CLI client is `ziwei-workspace-cli`, API audience and introspector are `ziwei-workspace-api`. Discovery, JWKS, token, introspection and revocation URLs must remain HTTPS under the configured issuer path and origin. Redirects are refused; requests time out in 5 seconds and failures never fall back to legacy authentication. HTTP loopback is possible only through the explicit injected test option, never a request parameter. Normal code/device flows request `openid workspace:read workspace:write`, never default `offline_access`.

## Routes and credentials

| Route | Behavior |
| --- | --- |
| `GET /api/identity/config` | Public sanitized mode/client/issuer/readiness/transport description. `ready` means local configuration is complete, not that DNS/TLS or the OP has been deployed. |
| `GET /api/identity/me` | Cookie or site AT; signature, current confidential introspection and native scope validation; returns `verified:true`, `verification:server`, stable identity, original user and scoped memberships. |
| `GET /api/identity/login` | Creates a five-minute single-use browser-bound state, nonce and PKCE S256 transaction. |
| `GET /api/identity/callback` | Exact configured callback, consumes transaction, checks signed ID token nonce/sub/sid and independently verifies the AT. Stores tokens only on the server, then redirects to the configured origin. |
| `POST /api/identity/logout` | Same-origin BFF Cookie logout; tombstones the current site session before revoking latest web AT/RT. Result says revocation `accepted`, `confirmed:false`, `allSitesLoggedOut:false`; HTTP 200 is not proof of OP inactivity. CLI separately revokes its public-client AT/RT directly at the discovered OP. |
| `POST /api/identity/backchannel-logout` | Signed RS256 `typ:Logout` token with logout event, issuer, exact web audience, bounded time, jti and sid/sub; persistent replay checks and sid/sub tombstones. |

`/api/auth/status` and `/api/auth/me` map to these real checks. Password login, registration, setup and all other old `/api/auth/*` paths are 403 in unified mode. Legacy Cookie/header sessions, opaque legacy Bearers, static MCP owner tokens, role/employee/email headers and old external API keys do not authenticate the unified human API. Existing explicitly authenticated daemon pairing/heartbeat, A2A and terminal machine protocols retain their original independent identity guards.

Cookies are host-only `__Host-` Secure/HttpOnly/SameSite=Lax cookies. Cookie-authenticated state-changing requests require the exact configured Origin and reject cross-site fetch metadata. BFF never returns AT/RT. Business requests reverify signatures, AT payload `typ:Bearer`, single site aud, allowed azp, iat/exp (300 seconds), introspection `token_type:Bearer`, active/sub/client/aud/exp consistency, issued/current roles and scope intersections, then native current membership/resource/device/employee guards. `admin` does not imply `read` or `write`; each operation names its required role and scope.

## Explicit native bindings

The preserved device heartbeat boundary additionally checks its explicit URL device ID against the paired credential, rejects conflicting body/query IDs, and supplies the authenticated paired device ID when heartbeat input omits one. Other task/action `params.id` values are never treated as device IDs. These checks have isolated memory-database route tests with a stubbed heartbeat business function.

`bindings.bind(...)` is a trusted server provisioning function, not an HTTP endpoint. A reviewed binding uses exact issuer/subject, an existing original `nativeUserId` and nonempty exact workspace IDs with current native memberships. No email lookup, automatic user creation, password copying or same-email merge occurs. Bindings are immutable; disable then review/provision a new identity rather than reassigning an old machine subject/client to another employee.

Human bindings retain their native member role. `kind:employee` additionally requires one existing employee owned by that native user in exactly one workspace. Interactive employees can use their own web/CLI subject without a machine client. Machine employees require a unique explicit `ziwei-workspace-worker-*` client and subject mapping; human clients cannot borrow a machine-bound subject. Employee resource calls currently allow only their bound employee/bot paths plus identity/membership metadata, and enforce the bound employee/device request targets. Broad employee/task collections are denied rather than granting an employee its owner's entire account scope.

New tables: `unified_identity_bindings`, `unified_identity_transactions`, `unified_identity_sessions`, `unified_identity_logout_replay`, `unified_identity_op_logout`. Session IDs in SQL are hashes of random Cookie tokens. Transactions consume by atomic DELETE RETURNING; session refresh uses SQL generation/CAS, a shared refresh lease, and local single flight. Logout/backchannel tombstones prevent late refresh or callback resurrection; refresh results that lose the CAS are explicitly revoked. Persistent state requires the same shared SQLite database and session encryption key; this is not a distributed multi-database session protocol.

## Verification and remaining acceptance

Offline tests use generated RSA keys, injected fetch, synthetic memory SQLite and `app.handle`; they do not listen on a port, call production, access real passwords, or execute real devices/tasks. Run:

```powershell
node --test backend/identity/identity.test.mjs backend/identity/sessions.test.mjs backend/identity/app.test.mjs
npm run lint
npm run build
```

Current intentional restrictions in unified mode: WS/SSE and mobile notification-v2 endpoints are rejected because their previous adapters rely on long-lived or legacy session state. The web UI polls ordinary notifications/tasks/conversation reads every 15 seconds and each call rechecks identity and native permissions. Existing workspace creation/invitation acceptance cannot expand immutable unified binding scope; bindings must be explicitly reviewed and provisioned. No global-logout UI is claimed; site logout does not end all realm SSO sessions.

The explicit management permission table covers employee environment reads/writes, terminal proxies, Git import/export, pairing, client update writes, employee deletion, phone configuration, binding writes and custom parameter writes. Each requires current site `admin`, `workspace:write`, and native Owner/Admin. Ordinary task/document writes retain `write`; HTTP DELETE is not automatically management. Static route matching follows Express case-insensitive segments and optional final slash, while captured workspace/resource IDs retain their exact case. The same normalization applies to notification stream rejection, machine exceptions and identity metadata paths.
